# CampusOverflow · PO 执行手册（逐条操作步骤）

> 适用：本项目 Product Owner（文档附录 F.1）
> 依据：《CampusOverflow 软件工程教学方案》L3 / L4 / L5 / Lab 2 / 第七章
> 用法：按周查第 0–7 章，写文档时直接抄第 8 章模板

---

## 0. 先明确你的边界（30 秒读完）

| 类别 | 内容 |
| --- | --- |
| **你负责** | 需求来源、优先级裁定、验收、演示、对外沟通（教师 / 助教 / 其他团队） |
| **你不负责** | 写代码、维护看板（SM）、主持会议流程（SM）、测试执行（QA） |
| **你会被打分的 4 件硬交付** | ① Product Backlog ② 用户故事地图 ③ Sprint Goal + 验收标准 ④ 4 次 Sprint Review 演示 |
| **你的最大风险** | 被判定"只做记录、不做决策"——即 PO 失位 |

**PO 失位的三种典型表现**（务必避免）
1. Backlog 全是"待定""待讨论"，没有优先级；
2. 每次 Review 都是开发同学在讲，你只负责翻页；
3. 教师问"为什么先做这个"，你答不出价值排序依据。

## 1. PO 的固定节奏（贴墙版）

| 频率 | 动作 | 耗时 | 产出 |
| --- | --- | --- | --- |
| 每天 | 扫一遍看板，只看"卡住超过 1 天的卡" | 5 min | 阻塞项转给 SM |
| 每天 | 与 SM 对 5 分钟：今天有无新需求 / 有无该拒的范围蔓延 | 5 min | 口头结论 |
| 每周 | 更新 Backlog 状态与优先级（有变化才改） | 20 min | `product-backlog.md` 更新 |
| 每 Sprint 第一周周一 | 主持 Sprint Planning | 40 min | Sprint Goal + Sprint Backlog |
| 每 Sprint 最后一周 | 主持 Sprint Review（演示 + 验收） | 每队 5 min | 评审纪要 |
| 每 Sprint 末 | 参与匿名互评（贡献度系数 0.7–1.3） | 10 min | 系数提交 |
| 每 Sprint 末 | Review 反馈转新故事，重排优先级 | 20 min | 下个 Sprint 候选故事 |
| 第 16 周 | 主持 8 分钟系统演示 + 答辩 | — | 答辩得分 |

## 2. W1–W2 · Sprint 0：开工准备（一次性）

### 步骤 1：建好目录骨架（10 分钟）

在你的团队仓库里确保存在以下目录（没有就建，用空 `.gitkeep` 占位后提交 PR）：

```
docs/
 ├── backlog/          # 你的一亩三分地
 │    ├── vision.md
 │    ├── interviews.md
 │    ├── product-backlog.md
 │    ├── rules-reputation.md
 │    ├── sprint-1-plan.md ...
 │    └── stories/US-Q-01.feature ...
 ├── domain/           # C 负责（你只读）
 ├── review/           # Review 纪要
 └── team/             # SM 负责
```

### 步骤 2：写《产品愿景声明》（30 分钟）

复制第 8.1 节模板，填完后提交 `docs/backlog/vision.md`。
**验收标准**：一个没上过软件工程课的人读完能说出"给谁用、解决什么痛点、凭什么比 Stack Overflow 更适合校园"。

### 步骤 3：写竞品分析（40 分钟）

做一张表，仅对比 3 列：`能力维度 | Stack Overflow | CampusOverflow 的校园化改造`。
必填维度：账号体系、内容组织、激励方式、教师参与、数据合规。
**产出**：`docs/backlog/vision.md` 的"竞品与差异化"小节。

### 步骤 4：组队与角色承诺书（Lab 1 现场 30 分钟）

1. 收集全组《个人技能矩阵自评表》（前端 / 后端 / 测试 / 运维 / 文档，各 1–5 分）；
2. 按**技能互补**组队，4–6 人；
3. 产出 PO / SM，其余为 Dev；你与 SM 必须由两人分任（文档 L5 明令反模式）；
4. 每人填写《角色承诺书》并签字，提交 `docs/team/role-commitment.md`。

### 步骤 5：产出 Backlog 初版 ≥ 20 条（60 分钟）

不要凭空想。按下面顺序做：

1. **先列 Epic**（四大子域）：身份与认证 / 问答核心 / 声誉激励 / 内容发现；
2. **每条 Epic 拆 4–8 条故事**，直接抄第 8.3 节的 24 条种子故事作为起点；
3. **只填 4 个字段**先落地：`ID / 作为…我希望…以便… / 优先级 / 归属 Sprint`；
4. Story Point 估算放到 Sprint 1 Planning 时和团队一起做（用 Planning Poker 或斐波那契 1/2/3/5/8/13）。

**优先级只用三档，不要用数字**：
- `P0 必须`：不做则业务闭环不通（Sprint 1–2 必须完成）
- `P1 应该`：显著影响体验（Sprint 2–3）
- `P2 可做`：锦上添花（Sprint 3–4 或加分项）

### 步骤 6：与 SM 一起确认看板（Lab 1 现场）

1. 四列：`To Do / In Progress / In Review / Done`；
2. WIP 限制：In Progress ≤ 3、In Review ≤ 3（写进看板设置，不是写进文档就完事）；
3. **明确规则**：卡片状态的变更必须与代码提交/PR 同时发生，禁止周末集中补状态；
4. 请 SM 在 Lab 1 结束时交看板截图（含 ≥ 5 条初始 Backlog）——这是 Lab 1 提交物之一，你配合提供卡片内容。

### 步骤 7：与技术负责人确认"做不了什么"（20 分钟）

找 C、D 确认技术约束并**当场记进 Backlog 备注**，例如：
- 第三方 OAuth 是否可选（方案中标注"可选"，需确认本周是否排入）；
- 全文搜索是否只做 LIKE（方案允许演进到 Elasticsearch，MVP 不做）；
- 邮件服务用真实 SMTP 还是 Mock。

这一步能挡住后面 80% 的"到 Sprint 结束才发现做不完"。

### Sprint 0 完成标准（自查）
- [ ] `vision.md` 已提交且能一句话说清差异化
- [ ] Backlog ≥ 20 条，每条都有 P0/P1/P2
- [ ] 24 条种子故事已按 Sprint 归属标好
- [ ] 看板四列 + WIP 已配置，截图已交
- [ ] 角色承诺书全员签字

## 3. W3–W6 · Sprint 1：身份与问答内核（你的重头戏）

> 本 Sprint 是文档里 PO 交付物最密集的阶段：访谈、故事地图、Backlog 终版、Gherkin、Planning、Review 全在这一段。

### 3.1 W3 之前：完成 3 份真实用户访谈（Lab 2 前置作业）

**操作步骤**

1. 定访谈对象：至少覆盖 1 名学生 + 1 名助教/研究生 + 1 名教师（三类角色各 1 份最稳）；
2. 每份访谈 20–30 分钟，**录音并转纪要**（先征得同意）；
3. 用统一提纲（第 8.2 节），**不要问"你想要什么功能"**，只问过去发生的事；
4. 24 小时内产出纪要，提交 `docs/backlog/interviews.md`；
5. 每条纪要末尾提炼一行 `洞察：…… → 需求假设：……`，这是后面写故事的依据。

**反例 vs 正例**
- ✗ 「你觉得需要一个搜索功能吗？」（引导式，无法证伪）
- ✓ 「上次你在课程群里找一道题的答案，花了多久？最后怎么找到的？」

### 3.2 Lab 2 现场主持脚本（2 学时 = 90 分钟）

你是主讲人，SM 负责计时与记录。

**Step 1 故事地图共建（45 min）**

1. （0–5 min）开场：宣布骨架——"用户从未注册到成为活跃贡献者"，把横轴写在白板最上方；
2. （5–10 min）横轴定序：`注册 → 浏览 → 提问 → 回答 → 互动 → 成长`，全组举手表决，不一致就投票；
3. （10–30 min）纵向贴卡：每人先独立写 5 张故事卡（便利贴/白板卡片），再依次贴到对应活动下，贴的时候必须口述一句"这个人想干什么"；
4. （30–40 min）去重合并：相同故事合并，保留语义更清楚的那张；
5. （40–45 min）**切 Walking Skeleton**：画一条横线，线上方是"最小可用闭环"（注册→提问→回答→看到回答），即 Sprint 1 MVP；
6. 收尾：让 E 导出 PNG，提交 `docs/domain/story-map.png`（方案要求提交到 domain 目录）。

**Step 2 Backlog 精化与 INVEST 评估（35 min）**

1. （0–20 min）把地图上的卡片转成规范句式，逐条写进 `product-backlog.md`；
2. （20–30 min）对照第 8.4 节 INVEST 六问逐条自检，不通过的**现场改写**（不是标记"待改"）；
3. （30–35 min）按"价值 / 成本"二维矩阵排序，产出与第 8.5 节一致的优先级。

**Step 3 Gherkin 验收标准（25 min）**

1. （0–10 min）你现场示范 1 条：把 `US-Q-01 发布问题` 写成 3 个场景（快乐 / 边界 / 异常）；
2. （10–22 min）全员分工，为 Sprint 1 承诺的每条故事写 ≥ 3 个场景；
3. （22–25 min）你逐条检查：**每个 Then 必须可测量**，出现"正确地""友好地"一律打回重写；
4. 提交 `docs/backlog/stories/<story-id>.feature`。

**Step 4 Sprint 1 Planning（15 min 现场 + 课后补足）**

按第 3.5 节的 40 分钟议程压缩执行，现场只完成"认领 + 落卡"。

### 3.3 W4 课后：Sprint 1 Backlog 终版（这是交作业的硬指标）

方案 L4 明确要求：**8–12 条 Sprint 1 用户故事**，含故事、验收标准、Story Point 估算，以 PR 形式提交主仓库。

**操作步骤**

1. 数与量对齐：`Sprint 1 Backlog = 8–12 条故事`，多了就砍到 Walking Skeleton 范围；
2. 每条补齐 6 个字段：`ID / 故事 / 验收标准链接 / Story Point / 负责人 / 状态`；
3. 用斐波那契估点，规则：**只有认领了这条故事的开发才能定分**，你只负责发现分歧（分歧 > 2 倍时说明故事没讲清，回去补验收标准）；
4. 计算总点数 = 团队本 Sprint 的承诺容量（Velocity 首 Sprint 无历史，用"人天 × 0.6"粗估）；
5. 提交 PR，标题：`docs(backlog): Sprint 1 Backlog 终版（含 Gherkin 与估点）`。

### 3.4 Sprint 1 Planning 议程（40 分钟，你主持）

| 时段 | 内容 | 你的动作 |
| --- | --- | --- |
| 0–5 min | 讲 Sprint Goal（一句话） | 只讲"为什么这个目标现在最重要"，不讲任务 |
| 5–15 min | 过 P0 故事 | 逐条念故事 + 验收标准，**不解释实现方案** |
| 15–30 min | 团队拆任务 + 估点 | 只记录分歧，不替开发做技术决策 |
| 30–35 min | 认领与落卡 | 确认每条故事有且仅有 1 名负责人 |
| 35–40 min | 确认 DoD 与风险 | 重申第 8.6 节的 DoD 九条 |

**Sprint Goal 写法（一行，含价值与可验证性）**
- ✗ 「完成 Sprint 1 的功能」
- ✓ 「让一名新用户能在 3 分钟内完成注册、发布第一个问题并收到一条回答——跑通业务最小闭环」

### 3.5 W6：Sprint Review 主持脚本（5 分钟/队）

1. （0:00–0:40）**你讲**：Sprint Goal 是什么 → 承诺了几条 → 完成几条（诚实报数，未完成的当场说明原因）；
2. （0:40–4:00）**开发讲 + 演示**：按"注册 → 提问 → 列表 → 回答"闭环走一遍真实系统，**禁止用 PPT 截图代替真机演示**；
3. （4:00–4:40）**提问**：请教师/其他团队提 2 个问题，你负责记录，不辩解；
4. （4:40–5:00）**你收口**：明确说明哪些反馈进 Sprint 2 Backlog、哪些明确不做及理由。

**Review 后 24 小时内必做**
1. 产出 `docs/review/sprint-1-review.md`（含得分、反馈清单、进 Backlog 的条目）；
2. 把反馈转成新故事，插入 `product-backlog.md` 并重排优先级；
3. 参加 Retro（SM 主持），你只贡献"需求侧"的改进项。

### 3.6 本 Sprint 你要跟队友对齐的接口

| 对象 | 对齐内容 | 时机 |
| --- | --- | --- |
| C | 身份认证的故事边界（是否含邮箱验证、OAuth 是否本 Sprint 做） | Planning 前 |
| D | `POST /api/v1/questions` 的入参字段（标题长度、标签数量上限） | 写 Gherkin 时 |
| E | 每条 Gherkin 场景能否自动化（可自动化 / 只能手工） | Lab 2 现场 |
| SM | 卡片拆分粒度（一条故事拆 2–5 个任务） | Planning 后 |

### Sprint 1 完成标准（自查）
- [ ] 3 份访谈纪要 + 洞察已提交
- [ ] 故事地图 PNG 已提交
- [ ] Sprint 1 Backlog 8–12 条，含估点与验收标准
- [ ] Review 用真机演示，未用截图代替
- [ ] 反馈已转为新故事并进入 Sprint 2 候选

## 4. W7–W10 · Sprint 2：互动与声誉

### 步骤 1：Planning 前先做"Backlog 减法"（20 分钟）

1. 打开 `product-backlog.md`，把 Sprint 1 未完成的故事**重新估点**（不要原样顺延，未完成通常意味着估低了）；
2. 把 Sprint 1 Review 的反馈故事插入，重新排序；
3. 划掉本 Sprint 不做的，**明确写出原因**（教师会问）。

### 步骤 2：主持 Sprint 2 Planning（40 分钟）

Sprint Goal 参考写法：
> 让一次"提问 → 回答 → 被采纳"能真实改变回答者的声誉值和个人主页徽章。

承诺故事：投票、采纳、评论、标签、声誉计算、个人主页（对应方案 2.5 里程碑）。

**注意**：本 Sprint 首次出现**跨模块协作**（QA 子域 → Reputation 子域）。你要在 Planning 上明确"一条故事的完成 = 端到端可演示"，而不是"后端接口写完"。

### 步骤 3：定义声誉规则的唯一来源（30 分钟）

与教师/助教确认并写进 `docs/backlog/rules-reputation.md`：

| 行为 | 分值 | 确认项 |
| --- | --- | --- |
| 回答被采纳 | +15 | 取消采纳是否回滚？ |
| 回答被赞 | +10 | 同一用户重复点赞如何处理？ |
| 回答被踩 | −2 | 是否设下限（不允许负分）？ |
| 教师悬赏 | 待定 | 积分来源、单题上限、结算时机 |

**这张表就是验收依据**，Review 时拿它逐条对数（方案 2.3.3 的原始规则）。

### 步骤 4：前端页面的验收要点（与 A/E 一起）

1. 问题列表页 `/questions`：按时间倒序、显示回答数、标签、票数；
2. 问题详情页 `/questions/:id`：投票按钮、回答列表、采纳按钮（仅提问者可点）；
3. 个人主页：声誉值、徽章、历史回答——**必须能被"投票"动作实时改变**，这是 Review 的演示点。

### 步骤 5：W10 Sprint 2 Review（演示脚本）

演示顺序（4 分钟内）：
1. 登录 → 提一个问题；
2. 另一个账号回答；
3. 切回提问者账号**采纳**该回答；
4. 打开回答者个人主页，展示声誉 +15 与徽章变化。

> 这一条链路就是本 Sprint 的"承诺兑现证明"，务必提前 1 天用真实环境彩排一遍。

### 步骤 6：开放 API 契约的 PO 验收（30 分钟）

1. 打开 Swagger UI（D 负责产出）；
2. 逐条对照你的 Gherkin 场景，检查**字段名与业务语言是否一致**（例如 `accepted` 还是 `isBest`——统一语言由 C 的术语表裁定）；
3. 发现不一致 → 开 Issue → 由 D 改 `openapi.yaml`，不要直接让前端"先凑合"。

## 5. W11–W13 · Sprint 3：发现与通知

### 步骤 1：守住范围（这是 PO 本阶段最重要的动作）

方案 2.3 明确：实时聊天、直播答疑、PDF 内嵌、AI 自动回答属**超出 MVP**，只能在 Sprint 4 之后作为加分项。

**拒绝范围蔓延的标准话术**（直接背）：
> 「这个想法很好，我记下来了。但本 Sprint 的承诺已经排满，插进来会让已在做的三条故事质量下降。我把它放进 Backlog 的 P2，Sprint 4 之后评估——如果需要提前，请你帮我指一条可以拿掉的等价故事。」

### 步骤 2：主持 Sprint 3 Planning

Sprint Goal 参考写法：
> 让一个用户不靠滚动列表，就能通过搜索和标签找到自己课程下的历史问题。

承诺故事：筛选、搜索、相关推荐、通知中心、悬赏。

### 步骤 3：确认通知的业务规则（20 分钟）

写进 `rules-reputation.md` 的"通知"小节，逐条确认：
1. 什么事件触发通知（被回答 / 被采纳 / 被 @）；
2. 通知失败**不得阻断主流程**（例如采纳成功但通知发失败，采纳仍算成功）；
3. 已读/未读的交互定义（点开即已读？还是手动标记？）。

### 步骤 4：教师悬赏的业务确认（找教师 15 分钟）

必问 3 个问题，答案直接写进文档：
1. 教师积分从哪来（无限额 / 学期配额）？
2. 单题悬赏上限多少？
3. 什么时候结算（采纳时 / 到期时 / 手动发放）？

### 步骤 5：W13 参与跨成员代码评审

由 E 指定你评审的 PR（不得评审自己的）。你评审时**只看业务侧三件事**：
1. 需求是否被完整覆盖（对照 Gherkin）；
2. 是否存在你没要求过的行为（超范围实现）；
3. 错误提示是否符合用户语言（不要暴露 `NullPointerException`）。

至少留 5 条实质意见（Lab 7 的提交物要求）。

### 步骤 6：W13 Review 演示脚本

演示顺序：搜索关键词 → 按课程标签筛选 → 展示相关推荐 → 触发一次通知并展示通知中心。

## 6. W14–W15 · Sprint 4：质量与部署

### 步骤 1：Planning——本 Sprint 你的工作量最小，但要守住"不承诺新功能"

Sprint Goal 参考写法：
> 让系统在校园网内可被真实访问，且每个核心流程都有自动化测试保护。

**你的动作**：
1. 明确宣布"本 Sprint 不做新业务功能，只做质量与部署"；
2. 把 P2 加分项故事放进 Backlog 但**不承诺**；
3. 与 B 确认上线时间点，倒排 Demo 彩排时间。

### 步骤 2：写 8 分钟 Demo 脚本（60 分钟）

**结构（每一段都要有一句"业务价值"解说）**

| 时间 | 演示内容 | 你必须说出口的一句话 |

### 步骤 3：组织上线"友测"（30 分钟）

1. 向其他团队发邀请（附 URL + 3 个测试任务，如"发一个问题并采纳一个回答"）；
2. 收集 ≥ 5 条外部反馈，记录到 `docs/review/friendly-test.md`；
3. 反馈里只挑 1–2 条**真正的缺陷**进修复清单，其余转 Backlog。

### 步骤 4：彩排（至少 1 次全流程）

1. 用**真实环境**（不是 localhost）跑一遍完整 Demo 脚本；
2. 掐表，超时就砍演示项，不要砍解说词；
3. 记录失败点（网络、数据被清空、账号密码），列成"演示前检查表"（见 7.4 节）。

### 8.4 INVEST 自检六问（每条故事念一遍）

| 字母 | 检查问题 | 不合格的表现 |
| --- | --- | --- |
| **I**ndependent | 这条故事能否独立开发与验收？ | 必须先做完另一条才能开始 |
| **N**egotiable | 是不是只写了"要什么"而没写"怎么实现"？ | 出现"用 Redis 缓存""加个定时任务" |
| **V**aluable | 对某个具体角色产生了什么价值？ | 说不出"以便…" |
| **E**stimable | 团队能不能给它估点？ | 估点分歧超过 2 倍 |
| **S**mall | 能不能在一个 Sprint 内做完？ | 一条故事 ≥ 13 点 |
| **T**estable | 验收标准能不能被机器或人工明确判定？ | 用"友好地""正确地"这类词 |

### 8.5 优先级矩阵操作（价值 / 成本）

1. 画 2×2：横轴成本（低/高）、纵轴价值（低/高）；
2. 全部故事标点；
3. 排序规则：**高价值低 ← 高价值高 ← 低价值低 ← 低价值高**（最后一类直接砍或放 P2）；
4. 把结果写回 `product-backlog.md` 的优先级列，并在 Sprint Planning 上说明排序依据。

### 8.10 贡献度系数匿名互评操作（每 Sprint 末）

**背景**：方案 7.3，系数 0.7–1.3，个人团队分 = 团队分 × 系数。

**操作步骤**
1. 由 SM 发起匿名表单（不含自己），每人给其他成员打 3 项：贡献量、协作配合、交付质量；
2. 各成员 3 项平均分 → 归一化到 0.7–1.3；
3. **你（PO）的职责**：提供"需求侧证据"给 SM 校验，而不是自己定分：
   - 谁按时交付了承诺的故事；
   - 谁的卡在 Review 时未通过验收；
   - 谁主动承接了 Review 反馈转化出的临时故事；
4. 你本人也要被评（把你自己也放进表单，由他人评）；
5. 结果由 SM 汇总、教师定稿，你不参与最终裁决。

> 红线：不得把"我跟你关系好"变成系数依据；教师的校验依据是 Git 提交、PR 质量、看板任务完成情况。

## 9. 翻车清单与应对（PO 专用）

| 翻车场景 | 早期信号 | 你的应对动作 |
| --- | --- | --- |
| Backlog 变成"许愿池"，条目只增不减 | 条目数 2 周内翻倍 | 每周固定 20 分钟做减法，砍掉的写进"变更记录 + 理由" |
| 故事被按技术层拆（前端一条、后端一条） | 出现"前端实现提问页"这种故事 | 打回重写：按业务价值切，参照方案 L4 反模式提醒 |
| 中途被塞需求 | 有人直接在 Planning 外提新功能 | 用第 5 章的标准话术拒绝，并记录到 Backlog P2 |
| 验收标准写成"友好地""正确地" | Gherkin 里出现形容词 | 当场要求改成可测量条件（数字、文案、状态） |
| Review 变成"PPT 汇报" | 演示只放截图 | 提前 1 天彩排真机演示，截图仅作兜底 |
| 演示时环境崩了 | 每次都靠 localhost | Review 前用真实测试环境，准备备用账号与热点 |
| 估点全靠你拍 | 你说了算，开发不参与 | 只有认领人能定分，你只负责暴露分歧 |
| 教师问"为什么先做这个"答不上来 | 排序没有依据 | 每次排序留一行依据（访谈证据 / 业务闭环 / 成本） |
| 团队分被个人系数拉低 | 有人连续两个 Sprint 低参与 | 提前 1 周私下提醒，并给一条可独立完成的小故事补贡献 |
| 答辩讲不清文档 | 文档像 AI 生成的"水"文 | 每份文档发 PR 前，自己脱稿讲一遍，讲不清就重写 |
